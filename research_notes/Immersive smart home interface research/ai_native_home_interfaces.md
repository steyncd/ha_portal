# AI-native, conversational and generative interfaces for the smart home (2025-2026), with emphasis on Home Assistant

Research date: 18 November 2026. Method note: Home Assistant release posts 2025.1 through 2026.11 were each opened and read (the 2026.5, 2026.6, 2026.10 and 2026.11 posts are longer than the reader's 100k-character window, so their tails were only partly read). The session's web-search budget ran out before every question was closed; anything not verified is listed under Gaps rather than guessed. Model names such as "GPT-6.1 Terra" or "Gemini 3.8 Flash" are reported exactly as the cited pages give them.

## 1. Home Assistant platform, release by release (2025.1 to 2026.11)

### Takeaway
Across 23 releases Home Assistant moved from "LLM as an optional voice agent" to a layered AI platform: `ai_task` entities (2025.8), a one-click MCP server with tool sets, admin gating and a read-only mode (2026.10 to 2026.11), visible tool-call traces in Assist (2025.12, 2026.4), and an admin-only "Home Assistant" LLM API that can read logs, history and reload integrations (2026.11). On the UI side the experimental Areas dashboard (2025.4) became the default "Overview" Home dashboard (2026.2) with usage-predicted "Common controls", and dashboards gained automation-grade visibility conditions and auto-updating "Automatic sections", but no release shipped a native floor-plan, 3D view or model-composed dashboard.

### Inferences
- The official trajectory is "adaptive but deterministic": usage-predicted Common controls, entity-driven card suggestions, automatic sections and rich visibility conditions adapt the UI without a model composing it. That leaves "ask a question, get a purpose-built card" open territory for a custom front end.
- "Sub-agents" in Home Assistant terms appear to be config **sub-entries** (multiple agents and AI Task entities per credential, 2025.7) rather than an orchestrated agent hierarchy; no release post describes agent-to-agent delegation.
- "AI-suggested automations" in core is limited to metadata ("Suggest with AI", 2025.8). 2026.7's tagline refers to human-readable purpose-specific triggers, not natural-language automation generation; the post only says clearer documentation "should help AI tools suggest better automations".
- The 2026.11 Home Assistant LLM API includes "reload config entry". For a household where reloads can disturb alarm state, that tool set should be excluded or the MCP URL run read-only.

### Gaps
- No native floor-plan or 3D feature was found in any 2025.1 to 2026.11 release post read; the nearest items are picture-elements editing improvements (2026.8, 2026.11), vacuum segment-to-area mapping (2026.3) and the Map dashboard (2026.10). The web-search budget ran out before I could check the public GitHub roadmap for a planned floor-plan feature.
- Whether "critical confirmations / protected entities" for Assist (planned in Voice chapter 10) shipped by 2026.11 is unverified; none of the release summaries I read mention it.
- The tails of the 2026.5, 2026.6, 2026.10 (about 29k characters) and 2026.11 (about 9k characters) posts were not fully read, so some patch-level items may be missing. One search snippet attributed the MCP read-only mode to "2026.10 beta notes"; the URL was the 2026.11 beta post and the final 2026.11 post confirms it there.
- No Voice chapter 12 or 2026 voice chapter was found; Voice Preview Edition sales numbers were not found.
- The full State of the Open Home 2026 keynote content (dashboard, voice and AI announcements) was not in the recap post and was not otherwise verified.

## 2. WebSocket / REST APIs a custom front end can use for AI features

### Takeaway
Everything the official frontend does for Assist is reachable over the same authenticated WebSocket: `assist_pipeline/run` streams microphone PCM in and STT, intent-progress deltas and a pre-announced streaming TTS URL out, while `conversation/process`, `logbook/event_stream`, `history/stream`, `camera/webrtc/offer`, `todo/item/subscribe` and `calendar/event/subscribe` cover text chat, narrative feeds, live video and lists. Floors and areas carry no geometry at all, and several of the most useful commands (`subscribe_trigger`, chat-log subscriptions, `llm/api/list`) are admin-only.

### Cited Findings
- Core WebSocket commands documented: auth flow, `supported_features` (`coalesce_messages`), `subscribe_events`, `subscribe_entities` (compact state stream with optional `entity_ids`), `subscribe_trigger` (admin only; send a `trigger` object and receive an `event` each time it fires), `call_service` (fields `domain`, `service`, `service_data`, `target` with `entity_id`/`device_id`/`area_id`/`floor_id`/`label_id`, and `"return_response": true`), `get_states`, `get_config`, `get_services`, `get_panels`, `ping`, `validate_config`, `extract_from_target`, `get_triggers_for_target` / `get_conditions_for_target` / `get_services_for_target`; `render_template`, `subscribe_condition`, `test_condition` and `execute_script` are named without detail — [HA WebSocket API docs](https://contributors.home-assistant.io/core/internals/websocket-api/)
- The developer docs have moved: `developers.home-assistant.io/docs/api/websocket`, `/docs/voice/pipelines/`, `/docs/core/llm/` and `/docs/intent_conversation_api` now 301-redirect to `contributors.home-assistant.io/core/internals/...` — [WebSocket API docs](https://contributors.home-assistant.io/core/internals/websocket-api/)
- `assist_pipeline/run` takes `start_stage` (`wake_word`, `stt`, `intent`, `tts`), `end_stage` (`stt`, `intent`, `tts`), `input`, optional `pipeline`, `conversation_id`, `device_id` and `timeout` (default 300 s); pipelines are listed with `assist_pipeline/pipeline/list` — [Assist pipelines docs](https://contributors.home-assistant.io/core/internals/assist-pipelines/)
- Audio is sent as binary WebSocket frames prefixed with one byte, the `stt_binary_handler_id` from `run-start`'s `runner_data`; format is raw 16-bit mono PCM at the declared `sample_rate` (resampled to 16 kHz); a frame containing only the handler byte ends the audio — [Assist pipelines docs](https://contributors.home-assistant.io/core/internals/assist-pipelines/)
- Event sequence: `run-start` (includes `tts_output` with `url`, `token`, `mime_type`, `stream_response`) > `wake_word-start/end` > `stt-start` > `stt-vad-start` > `stt-vad-end` > `stt-end` (`stt_output.text`) > `intent-start` > `intent-progress` (repeatable; carries `chat_log_delta` or `tts_start_streaming`) > `intent-end` (`intent_output`, `processed_locally`) > `tts-start` > `tts-end` > `run-end`; errors include `stt-no-text-recognized`, `intent-failed`, `wake-word-timeout`, `duplicate_wake_up_detected`, `timeout` — [Assist pipelines docs](https://contributors.home-assistant.io/core/internals/assist-pipelines/)
- When starting at `wake_word`, the server accepts `noise_suppression_level` (0-4), `auto_gain_dbfs` (0-31) and `volume_multiplier` — [Assist pipelines docs](https://contributors.home-assistant.io/core/internals/assist-pipelines/)
- Text conversation: REST `POST /api/conversation/process` and WebSocket `conversation/process` with `text`, `language`, `agent_id` (default `conversation.home_assistant`), `conversation_id`, `device_id`, `satellite_id`; the response has `response.response_type`, `response.speech.plain.speech`, `response.data` (`success`/`failed` target lists typed `floor`, `area`, `domain`, `device_class`, `device`, `entity`, `custom`), `conversation_id` and `continue_conversation`; error codes `no_intent_match`, `no_valid_targets`, `failed_to_handle`, `unknown` — [Conversation API docs](https://contributors.home-assistant.io/core/internals/conversation-api/)
- Other conversation commands in core source: `conversation/agent/list`, `conversation/prepare`, `conversation/sentences/list` (admin), `conversation/agent/homeassistant/debug`, and admin-only `conversation/chat_log/subscribe` (needs `conversation_id`; emits `INITIAL_STATE` then per-event updates) and `conversation/chat_log/subscribe_index` — [conversation/http.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/conversation/http.py)

### Inferences
- A browser push-to-talk button is fully supported by the platform: capture with an AudioWorklet, downsample to 16 kHz PCM, start `assist_pipeline/run` with `start_stage: "stt"`, `end_stage: "tts"`, stream frames with the handler byte, render `intent-progress` deltas as live text, and start an `<audio>` element on the `tts_output.url` from `run-start` so speech begins while the LLM is still generating.
- Text chat with token streaming should use `assist_pipeline/run` with `start_stage: "intent"` and `end_stage: "intent"` rather than `conversation/process`, because only the pipeline emits `intent-progress` deltas.
- `ai_task.generate_data` via `call_service` with `return_response: true` gives a front end schema-constrained LLM output without holding any API key, but it runs with the model configured in Home Assistant; the Cloud Functions path is still needed for provider-specific features (Live audio, long context, caching).
- Because floors and areas have no geometry, any spatial or 3D view must keep its own geometry store keyed by `area_id` / `floor_id` (for example in Firestore or a static asset), then join registry data at runtime.
- The front end's token determines what is possible: a non-admin user cannot use `subscribe_trigger` or chat-log subscriptions. A read-only "narrator" role and an admin "operator" role map naturally onto separate HA users.

- Whether long-lived access tokens still work against `/api/mcp` (useful for a Cloud Function client) is not stated on the integration page.

## 3. Camera and vision AI

### Takeaway
Frigate went from embeddings-based semantic search (0.15/0.16) to structured GenAI review summaries with threat levels (0.17) and a built-in tool-calling "Chat" agent with a recap tool (0.18), all runnable locally. Commercial equivalents (Gemini for Home, Ring, Wyze) cost about USD 20 per month, and independent reviews consistently found Gemini's daily "Home Brief" narratives inventing people and events, which is the main design lesson for any narrated recap.

### Cited Findings
- Frigate 0.16.0 (16 August; year not shown on the page): face recognition (sub-labels for known faces), built-in licence-plate recognition with friendly labels for known plates, Semantic Search made optional and decoupled from GenAI, Jina V2 multilingual embeddings, D-FINE / RF-DETR / YOLOv9 detector support, bird classification — [Frigate v0.16.0](https://github.com/blakeblackshear/frigate/releases/tag/v0.16.0)
- Frigate 0.17.0 (27 February): GenAI **review summaries** with title, description and threat classification; custom **state** and **object classification** models trained locally (MobileNetV2), for example "gate open or closed"; fully local audio transcription (sherpa-onnx or faster-whisper); per-camera semantic-search **triggers**; camera wizard; go2rtc `exec`/`expr`/`echo` sources disabled by default — [Frigate v0.17.0](https://github.com/blakeblackshear/frigate/releases/tag/v0.17.0)

### Inferences
- "Search my footage in natural language" in practice is two different mechanisms: (a) CLIP-style embedding similarity over thumbnails (Frigate Semantic Search: fast, local, fuzzy, no reasoning), and (b) LLM-written text descriptions that are then embedded or searched (Frigate object descriptions and review `scene` text, Ring/Google captions). Frigate 0.18 Chat layers an agent on both. A custom front end can get most of the value by querying Frigate rather than re-implementing vision.
- A "daily narrated recap" on this stack is cheap if it is text-over-text: Frigate already holds per-review `title`/`scene`/`potential_threat_level`; summarising a day's worth is a single small LLM call. Rough cloud cost if frames are sent instead: 100 review items/day x 20 preview frames, assuming about 260 tokens per small image (assumption, not verified this session), is about 0.5M input tokens/day, which is about USD 0.15/day on `gemini-3.5-flash-lite` plus a few cents of output, or roughly USD 5 to 8/month; fully local costs only GPU power.
- The Gemini for Home reviews argue for a recap that is grounded and checkable: every sentence should link to the clip or review item it came from, identities should come only from Frigate's face/plate sub-labels (never from the LLM), and low-`confidence` items should be omitted or flagged.
- Since the household already has LPR, the differentiated features are review-level threat triage, custom state classification (gate open/closed as a vision-derived sensor, useful as an independent check on the gate contact), semantic triggers, and conversational search.

## 4. Generative / adaptive UI

### Takeaway
By late 2026 the field has settled into three tiers: controlled (the model picks from pre-built components), declarative (the model emits a JSON/DSL spec constrained to a catalogue: Google A2UI, Vercel json-render, OpenUI Lang) and open-ended (the model or a tool ships HTML into a sandboxed iframe: MCP Apps, OpenAI Apps SDK, Google's Gemini "dynamic view"). json-render ships an official Svelte 5 renderer, which makes the declarative tier directly usable here. I found no shipped example of runtime model-composed dashboards for Home Assistant; existing projects use LLMs to author Lovelace YAML ahead of time.

### Cited Findings
- Google Research's "Generative UI" (18 Nov 2025) has Gemini 3 Pro emit full HTML/CSS/JS per prompt using tool access (image generation, search), detailed system instructions and post-processors; it shipped as "dynamic view" and "visual layout" experiments in the Gemini app and in Search AI Mode; raters preferred human-expert sites most, with generative UI close behind and well ahead of markdown output; generation can take "a minute or more" — [Google Research blog](https://research.google/blog/generative-ui-a-rich-custom-visual-interactive-user-experience-for-any-prompt/)
- A2UI is Google's Apache-2.0 declarative spec: agents send UI as structured data and the client renders it with its own widgets from a catalogue both sides know; components outside the catalogue are ignored (search summary) — [Google Developers Blog, introducing A2UI](https://developers.googleblog.com/introducing-a2ui-an-open-project-for-agent-driven-interfaces/)
- A2UI v0.9 (17 Apr 2026) renamed the optional component set from "Standard" to "Basic", added an official React renderer alongside Lit, Angular and Flutter, a shared web-core library, an Agent SDK (`pip install a2ui-agent-sdk`) with custom catalogues via `CatalogConfig.from_path`, **dynamic catalogues** switchable at runtime "to match user permissions or device constraints", client-defined functions and client-to-server data syncing; transports named are A2A, AG-UI, MCP, WebSockets and REST — [A2UI v0.9 post](https://developers.googleblog.com/a2ui-v0-9-generative-ui/)
- json-render (vercel-labs, Apache-2.0): `defineCatalog(schema, {...})` from `@json-render/core` declares components with Zod `props` and a `description`, plus actions; `defineRegistry` maps them to real components; the spec is a flat `elements` map with a `root`; props can bind with `{"$state": "/path"}`, `{"$bindState": "/path"}`, `$cond`, `$template`, `$computed`; elements have `visible` conditions and `watch`; `createSpecStreamCompiler` renders partial specs as they stream; `catalog.prompt()` generates the system prompt — [json-render README](https://github.com/vercel-labs/json-render)
- json-render renderers include `@json-render/react`, `@json-render/vue`, **`@json-render/svelte` (Svelte 5)** with `@json-render/shadcn-svelte`, `@json-render/solid`, `@json-render/react-native`, and `@json-render/mcp` for MCP Apps hosts — [json-render README](https://github.com/vercel-labs/json-render)
- MCP Apps (SEP-1865, announced 21 Nov 2025 by MCP maintainers at Anthropic and OpenAI with the MCP-UI authors): UI templates are predeclared `ui://` resources, tools reference them through `_meta` `"ui/resourceUri"`, content is `text/html` in sandboxed iframes, and the UI talks to the host with MCP JSON-RPC over `postMessage`; security rests on sandboxing, reviewable predeclared templates, auditable messages and user consent for UI-initiated tool calls — [MCP blog](https://blog.modelcontextprotocol.io/posts/2025-11-21-mcp-apps/)
- The SEP is now marked Final with extension id `io.modelcontextprotocol/ui`; secondary sources say it has been stable since the 2026-01-26 spec revision and ships in Claude, ChatGPT, VS Code and Goose (search summary) — [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp)
- OpenAI's Apps SDK launched at DevDay on 6 Oct 2025; widgets use `window.openai` (`setWidgetState`, `callTool`, follow-up messages); ChatGPT now implements the MCP Apps standard and OpenAI advises using the standard keys first and `window.openai` only for ChatGPT-specific features (search summary) — [OpenAI: MCP Apps in ChatGPT](https://developers.openai.com/apps-sdk/mcp-apps-in-chatgpt)
- CopilotKit's taxonomy (29 Jan 2026): static/controlled (AG-UI streaming with frontend tools; strongest control and brand consistency), declarative (A2UI, Open-JSON-UI; shared control), open-ended (MCP Apps; most flexible, with security, performance, styling and portability concerns); AG-UI itself is an event/state protocol under all three, not a UI spec; recommendation is to start static and reserve open-ended for complex cases — [CopilotKit guide](https://copilotkit.ai/blog/the-developer-s-guide-to-generative-ui-in-2026)
- Thesys C1 documentation now redirects to OpenUI, "the open standard for Generative UI", built around "OpenUI Lang", a compact line-streamed language over your own component library that the site claims needs under half the tokens of JSON formats, with "Autofix" for invalid output and integrations listed for Vue, Angular, Svelte and React Native — [OpenUI docs](https://www.openui.com/docs?from=c1&utm_source=docs.thesys.dev&utm_medium=redirect)
- Anthropic's "Imagine with Claude" was a short research preview released alongside Claude Sonnet 4.5 in which the interface is generated as the user clicks through it; coverage describes it as a feasibility study limited to Max subscribers (secondary sources only) — [TestingCatalog](https://www.testingcatalog.com/anthropic-experiments-with-an-agent-for-gereating-ui-on-the-fly), [heise](https://heise.de/-10699104)
- Home Assistant projects found use LLMs to write dashboards ahead of time: AI Agent HA generates a dashboard from a request and adds it to the sidebar; "Claude Chat for Home Assistant" (3 May 2026) stages edits with `propose_dashboard_update`, shows a unified diff and writes nothing until the user clicks Apply; reads are ungated while dashboard updates, service calls and automation changes require approval — [ai_agent_ha](https://github.com/sbenodiz/ai_agent_ha), [Claude Chat forum post](https://community.home-assistant.io/t/claude-chat-for-home-assistant-chat-panel-dashboard-editing-with-diff-approval/1009040)
- Home Assistant's own adaptive steps are deterministic: usage-predicted "Common controls" (2025.10), per-entity suggested cards with a `getEntitySuggestion` hook for custom cards (2026.6), registerable dashboard strategies (2026.5), visibility conditions for Sun/Zone/Template/Device (2026.10) and automatic sections (2026.11) — [2025.10](https://www.home-assistant.io/blog/2025/10/01/release-202510/), [2026.6](https://www.home-assistant.io/blog/2026/06/03/release-20266/), [2026.10](https://www.home-assistant.io/blog/2026/10/07/release-202610/), [2026.11](https://www.home-assistant.io/blog/2026/11/04/release-202611/)
- Emporia's AI Energy Assistant (3 Dec 2025) is a domain example of "ask a question, get a purpose-built view": it answers energy questions and "build[s] custom visualizations" over an Emporia MCP server, with stated limits (slower with 10+ devices, weak mobile rendering of complex visuals, about 50 messages/day) — [Emporia blog](https://www.emporiaenergy.com/blog/meet-emporia-ai-energy-assistant/)

### Inferences
- The safe pattern for a home dashboard is the declarative tier: define a small catalogue of existing Svelte components (stat tile, trend chart, camera still, entity list, timeline, Sankey, comparison bar, action button), let the model emit a spec that references `entity_id`s and time ranges only, validate the spec against Zod plus a registry-derived allow-list of real entity ids, and have the client fetch live data itself through `subscribe_entities`, `history/stream` and `recorder` statistics. The model never supplies numbers, so it cannot hallucinate state.
- Actions in the catalogue should be typed intents (for example `toggle_light`, `set_scene`, `open_camera`) rather than raw `call_service`; high-risk intents are simply absent from the catalogue, which is a stronger guarantee than prompt instructions. A2UI's "dynamic catalogues by user permission or device" maps onto child vs adult vs wall-display profiles.
- Streaming matters for perceived latency: json-render-style partial rendering lets a card skeleton appear in under a second while the rest streams, whereas Google's full-HTML approach (up to a minute or more) is unsuitable for glanceable home UI.
- Context-driven rearrangement (time, presence, alarm state) does not need a model at request time. A model can periodically propose layout rules or rank cards (cached per user and time bucket, like HA's 24-hour usage-prediction cache), with deterministic rendering in between.
- MCP Apps is the route for exposing the same cards outside the PWA (for example inside Claude or ChatGPT via the HA MCP server), but it is an iframe model and offers no advantage inside one's own app.

### Gaps
- Apple's adaptive widgets, Smart Stack suggestions and Home-app adaptive features were not researched (search budget exhausted).
- No authoritative Anthropic source for "Imagine with Claude" was opened; details rest on secondary coverage.
- The relationship between Thesys C1 and OpenUI (rename, open-sourcing, licence, pricing) is not stated on the page read.
- No evidence was found of a production smart-home product that composes its dashboard with a model at runtime, nor any user study of such a UI; absence here reflects limited searching, not proof that none exists.
- The A2UI message-type names and its formal security model were not in the v0.9 post and were not verified from a2ui.org.

## 5. Proactive and agentic homes, and safety

### Takeaway
Community practice and Home Assistant's own platform changes converge on one rule: prompts are instructions, tool availability is the control. Proactive features that work in 2026 pair deterministic detection (rules, logbook pattern mining, device-silence learning) with an LLM used only to explain or triage. For a house with an alarm, an electric gate and cameras covering children, disarming, opening, unlocking, camera/detection toggles, configuration changes and any identity claim about a person must stay behind a human confirmation enforced outside the model.

### Cited Findings
- Home Assistant 2026.11 states that with the new tools assistants "can change your setup, not just read it", advises giving assistants "the access you are comfortable with and no more", makes any LLM API available only after an administrator attaches it to a conversation agent or the MCP server, and restricts continuing an AI conversation to the user who started it — [2026.11](https://www.home-assistant.io/blog/2026/11/04/release-202611/)
- The MCP server's "Read-only" option excludes "Call action", "Reload config entry" and device-control tools; per-tool-set URLs are never read-only; "Device control" reaches only entities exposed to voice assistants, whereas the "Home Assistant" set can read all entities, logs and history and perform actions and always requires an administrator — [MCP server integration](https://www.home-assistant.io/integrations/mcp_server/)
- LLM tools declare `read_only`, `destructive`, `idempotent` and `open_world` annotations, with defaults that "assume the worst"; custom APIs can set `requires_admin=True` — [LLM API docs](https://contributors.home-assistant.io/core/internals/llm-api/)
- Platform hardening in 2026: installing or skipping updates and Z-Wave lock user/credential actions require an admin (2026.9); `mqtt.publish`, `mqtt.dump` and Synology reboot/shutdown require an admin when called directly by a user (2026.10); refresh tokens are revoked when a user is removed (2026.10.2) — [2026.9](https://www.home-assistant.io/blog/2026/09/02/release-20269/), [2026.10](https://www.home-assistant.io/blog/2026/10/07/release-202610/)
- Community guide "So You Want to AI in Home Assistant" (19 Aug 2026): "One is an instruction. The other is a control."; "Packaging is not permissioning."; "Home Assistant controls which entities are exposed."; keep reliability-critical automations (leak shut-off, smoke alarm, basic climate) independent of inference; shape entity lists into summaries because a short spoken request can become thousands of prompt tokens — [HA community guide](https://community.home-assistant.io/t/so-you-want-to-ai-in-home-assistant/1021777)
- Home Generative Agent (HACS, LangGraph; minimum HA 2026.8) pairs an LLM agent with a deterministic "Sentinel" engine that flags unlocked locks, open entries and unknown people and pushes alerts: "the LLM advises but never actuates"; a "Critical Action PIN" holds unlock or garage-open automations for confirmation; the agent sees only entities exposed to Assist; MAC/IP addresses and hostnames are redacted before reaching the chat model; long-term memory is semantic search in PostgreSQL/pgvector; only an administrator can enrol faces — [home-generative-agent](https://github.com/goruck/home-generative-agent)
- Other community projects enforce confirmation outside the model: an "entity allowlist, confirmation for risky actions, state verification after each call, audit log" design; a chat agent that asks before unlocking locks or disarming alarms by default (search summary) — [home-assistant-llm-agent](https://github.com/walidsadfi-evolurise/home-assistant-llm-agent), [ha-llm-agent](https://github.com/rgerr/ha-llm-agent)
- Automation Suggestions (HACS, no LLM at runtime) mines the logbook for repeated manual actions with defaults of a 14-day look-back, minimum 2 occurrences and a 30% consistency threshold, scores each suggestion 0-1, exposes `sensor.automation_suggestions_count` / `_top`, services `automation_suggestions.analyze_now` and `.dismiss`, a `custom:automation-suggestions-card`, and flags stale automations (never triggered, inactive 30+ days, disabled) — [home-assistant-automation-suggestions](https://github.com/Danm72/home-assistant-automation-suggestions)
- AI Automation Suggester (HACS) sends entities, areas, devices and existing automations (not logbook history) to OpenAI, Anthropic, Google, Groq or Ollama and returns YAML suggestions as notifications (search summary) — [ai_automation_suggester](https://github.com/ITSpecialist111/ai_automation_suggester)
- Health/"what changed" projects surfaced: Device Sentinel (learns each device's reporting rhythm to spot frozen hardware, with a daily brief), HA Sentinel v0.1.0 ("what stopped working, since when, what it depends on"), and a "HeartBeat" periodic LLM summary of changes over a 1 to 24 hour look-back (search summaries; posts not opened) — [Device Sentinel](https://community.home-assistant.io/t/device-sentinel-detect-frozen-hardware-with-device-learning/1029252), [HA Sentinel](https://community.home-assistant.io/t/ha-sentinel-what-stopped-working-since-when-what-it-depends-on-testers-wanted/1029332), [HeartBeat](https://community.home-assistant.io/t/home-assistant-heartbeat-periodic-home-devices-heartbeat-with-llm-summary/884847)
- Home Assistant's own Activity details dialog (2026.9) already reconstructs the causal chain for any change (trigger > automation/script > entity change), and `logbook/get_events` accepts a `context_id` — [2026.9](https://www.home-assistant.io/blog/2026/09/02/release-20269/), [logbook/websocket_api.py](https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/logbook/websocket_api.py)
- "Invitation Is All You Need!" (Nassi, Cohen, Yair; arXiv 2508.12175) demonstrated 14 indirect prompt-injection scenarios against Gemini-powered assistants through emails, calendar invitations and shared documents, including "control of home automation devices"; its threat analysis rated 73% of threats High-Critical, and Google deployed dedicated mitigations — [arXiv 2508.12175](https://arxiv.org/abs/2508.12175)
- Press coverage of that work describes a poisoned calendar invite causing Gemini to operate lights, windows and a boiler when the user later asked for a summary; Google said it accelerated defences including more user-confirmation requirements (search summary) — [Engadget](https://www.engadget.com/cybersecurity/researchers-hacked-google-gemini-to-take-control-of-a-smart-home-201926464.html)
- "PromptShield Home" (arXiv 2608.05495, 6 Aug 2026) studies ambient injection, where TV speech, on-screen text or overheard conversation look like commands to a multimodal home agent; on a 19-scenario pilot benchmark with execute / block / ask_user decisions, every MLLM configuration over-refused (unsafe-execution rate near 0% but safe-completion rate near 0% too) and missed a true fall, adding ASR transcripts reduced safety, and an always-block baseline scores 82% accuracy; the authors recommend "Route, Don't Replace" (physical sensors as the gate, the MLLM as a specificity filter, ask the user when uncertain) — [alphaXiv 2608.05495](https://www.alphaxiv.org/abs/2608.05495)
- Alexa+ context: Amazon says upgraders increase smart-home engagement by nearly 50% in the first month and set up twice as many routines; a July 2026 AI-powered smart-home developer toolkit is in preview (search summary) — [Amazon developer blog](https://developer.amazon.com/alexaplus/blogs/2026/07/alexa-plus-new-ways-to-build-experiences)

### Inferences
**Actions that should never be delegated to a model without an out-of-band human confirmation** (derived from the sources above plus this household's hardware):
- Alarm: disarm, bypass zones, change arm mode downward, change codes. Arming is lower risk but should still be confirmed if it could trap or false-trigger.
- Gate, garage, locks: open or unlock, and "hold open". Closing can also be hazardous for a motorised gate (people, vehicles, children in the path), so treat both directions as confirm-only.
- Cameras and detection: turning cameras, recording, detection, Frigate profiles or notifications off; privacy-mode toggles; deleting recordings or exports; sharing clips or stills outside the household. Frigate 0.18 Chat itself has a "toggle camera features" tool, so the same caution applies there.
- Children on camera: no face enrolment, identity naming or presence claims about children by a model; identities only from deterministic recognisers; avoid sending frames of children to cloud models at all where a local model or text-only summary will do; never expose live child-camera streams through an agent tool.
- Configuration: creating, editing, enabling or disabling automations, scripts and scenes; reloading integrations or YAML; restarts; update installs; user, token and exposure changes; MQTT publishes.
- Safety-relevant loads: geyser/boiler, heaters, stove or oven plugs, pool pumps, inverter and battery modes, EV charging limits.
- Anything triggered by untrusted content the model has read: calendar entries, emails, web pages, notification text, device and entity names from third parties, text visible in camera frames, and transcribed audio.

**Enforcement patterns that hold up**
- Capability tiers by token, not by prompt: a read-only narrator (MCP "Read-only", or a non-admin HA user with no exposed sensitive entities), a comfort actor (lights, media, climate set-points within bounds via an allow-list), and no model-reachable path for the items above.
- Confirmation in the client, not in the conversation: the model emits a proposed action object; the PWA renders a native confirm sheet showing the exact service call and target; the WebSocket call is made by the UI code under the signed-in user's token after an explicit tap (optionally with WebAuthn/passkey step-up for alarm and gate). A model saying "the user confirmed" must have no effect.
- Verify and log: read back state after each call, write an audit entry (who, what, model, prompt hash), and surface it in the Activity feed.
- Proactive digests should be composed from deterministic findings (Sentinel-style rules, statistics deltas, device silence), with the LLM limited to phrasing and prioritising; every claim should link to the entity history or clip that supports it.
- Per-family-member memory is best kept as explicit, user-visible preference records keyed by HA user id (viewable and deletable), rather than opaque conversation memory; HA's own usage prediction is already per user.

### Gaps
- No official Home Assistant security guidance on prompt injection specifically (for example text in camera frames or malicious entity names) was found; the search returned only community material.
- No source was found describing per-user long-term memory in Home Assistant core; HGA's pgvector memory is the only concrete implementation located, and its per-user scoping is not documented on the page read.
- Whether Assist's planned per-entity "critical confirmation" exists in 2026.11 is unverified (see section 1 gaps).
- Chapters 6 to 10 of the community AI guide (likely covering safety and memory in more depth) were beyond the portion read.
- No incident reports of real-world harm from LLM-controlled Home Assistant installs were found; this was not searched exhaustively.

## 6. Voice and multimodal in the browser

### Takeaway
For an iPhone/iPad PWA the realistic options in late 2026 are (a) Home Assistant's own pipeline over the existing WebSocket for push-to-talk, with streaming TTS giving roughly 0.5 s time-to-first-audio, and (b) a cloud speech-to-speech session (OpenAI Realtime over WebRTC or Gemini Live over WebSocket) brokered by a Cloud Function that mints ephemeral credentials, where barge-in is handled server-side. Chrome's built-in Gemini Nano does not run on iOS or Android, so on-device browser AI is a desktop/wall-display-only enhancement.

### Cited Findings
- Home Assistant pipeline from a browser: 16-bit mono PCM frames over the WebSocket with a one-byte handler prefix; `start_stage` can be `wake_word`, `stt`, `intent` or `tts`; server-side VAD emits `stt-vad-start` / `stt-vad-end`; `run-start` pre-announces the TTS URL with `stream_response` — [Assist pipelines docs](https://contributors.home-assistant.io/core/internals/assist-pipelines/)
- Streaming TTS reduced time-to-first-speech for long LLM answers from over 5 s to about 0.5 s on both Home Assistant Cloud and Piper — [Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11)
- Home Assistant UI hooks for voice: the Shortcut card/badge "Launch Assist" action (2026.5), Assist from Quick search (2026.8), Android on-device microWakeWord (2026.3), and a Labs "Two-way audio" talk button on camera streams that requires HTTPS (2026.11) — [2026.5](https://www.home-assistant.io/blog/2026/05/06/release-20265/), [2026.8](https://www.home-assistant.io/blog/2026/08/05/release-20268/), [2026.3](https://www.home-assistant.io/blog/2026/03/04/release-20263/), [2026.11](https://www.home-assistant.io/blog/2026/11/04/release-202611/)
- OpenAI Realtime over WebRTC: the browser adds a mic track and an `oai-events` data channel, then either posts its SDP to your server (which calls `https://api.openai.com/v1/realtime/calls`) or fetches an ephemeral key your server minted at `https://api.openai.com/v1/realtime/client_secrets` and posts the SDP itself; the docs example uses model `gpt-realtime-2.1`; WebRTC gives "more consistent performance" than WebSockets for clients — [OpenAI Realtime WebRTC guide](https://developers.openai.com/api/docs/guides/realtime-webrtc)
- The same guide documents a newer "GPT-Live" WebRTC path (`POST /v1/live/sessions`, example model `gpt-live-1` delegating to `gpt-5.6-terra`), with 15 seconds of voice billed at session creation — [OpenAI Realtime WebRTC guide](https://developers.openai.com/api/docs/guides/realtime-webrtc); a search summary conflicts, saying GPT-Live launched 8 Jul 2026 as a ChatGPT feature not exposed as a developer API — [third-party summary](https://aitechconnect-976.pages.dev/news/openai-realtime-audio-trio-voice-agents)
- OpenAI barge-in: over WebRTC/SIP "the server will automatically truncate unplayed audio when there's a user interruption"; over WebSocket the client must stop playback on `input_audio_buffer.speech_started` and send `conversation.item.truncate` with `audio_end_ms`; push-to-talk uses `response.cancel` and (WebRTC) `output_audio_buffer.clear`; tools are declared in `session.update` and results returned with a `function_call_output` item then `response.create` — [OpenAI Realtime conversations guide](https://developers.openai.com/api/docs/guides/realtime-conversations)
- OpenAI turn detection: `server_vad` (`threshold`, `prefix_padding_ms`, `silence_duration_ms`) or `semantic_vad` (`eagerness` low/medium/high/auto), with `create_response` and `interrupt_response` flags — [OpenAI Realtime VAD guide](https://developers.openai.com/api/docs/guides/realtime-vad)
- OpenAI Realtime pricing reported by third parties: `gpt-realtime-2.1` at USD 32 per 1M audio input tokens (USD 0.40 cached) and USD 64 per 1M audio output tokens, with a mini variant around USD 10 / 20 (not verified on OpenAI's pricing page) — [third-party pricing roundup](https://aireiter.com/blog/openai-realtime-api-pricing)
- Gemini Live API: stateful WSS; browser can connect client-to-server ("generally performs better for audio and video streaming") using **ephemeral tokens** in production; input 16-bit PCM 16 kHz, output 24 kHz; JPEG video frames at up to 1 frame per second; barge-in supported ("users can interrupt the model at any time"); function calling and Google Search; 70 languages — [Gemini Live API docs](https://aistudio.google.com/docs/live-api)
- Gemini Live pricing: `gemini-3.8-live`, `gemini-3.8-live-extended-thinking` and `gemini-3.1-flash-live-preview` at USD 3.00 per 1M audio input tokens (USD 0.005/min), USD 12.00 per 1M audio output (USD 0.018/min) and USD 1.00 per 1M image/video input (USD 0.002/min), with a free tier — [Gemini API pricing](https://aistudio.google.com/docs/pricing)
- Chrome Prompt API (Gemini Nano): shipped to web pages in Chrome 148 and extensions in Chrome 138; needs 22 GB free disk, more than 4 GB VRAM or 16 GB RAM with 4+ cores; supports text, image and audio input (audio needs a GPU), text-only output, and JSON-Schema `responseConstraint`; languages en/ja/es/de/fr; **not supported on Chrome for Android or iOS** — [Chrome Prompt API docs](https://developer.chrome.com/docs/ai/prompt-api)
- In-browser ASR: Transformers.js exposes Whisper via the `automatic-speech-recognition` pipeline with `device: 'webgpu'`; Hugging Face's Moonshine Web demo runs Moonshine Base locally with WebGPU and a WASM fallback; one comparison reports Whisper Tiny at 10 to 15x real time on WebGPU (blog sources without reproducible methodology; search summaries) — [Moonshine Web README](https://huggingface.co/spaces/webml-community/moonshine-web/blob/main/README.md), [offlinetts comparison](https://offlinetts.com/blog/browser-speech-recognition-whisper-comparison/)
- Pointing a camera at something: the Gemini Live API accepts camera frames (Google suggests 768x768 at 1 FPS per an older API page), and Home Assistant's `ai_task.generate_data` / `ai_task.evaluate` accept image attachments by `media_content_id` — [Gemini Live API docs](https://aistudio.google.com/docs/live-api), [AI Task integration](https://www.home-assistant.io/integrations/ai_task/)

### Inferences
- Recommended default: push-to-talk through `assist_pipeline/run` (keeps STT/TTS/agent choice and entity exposure inside Home Assistant, works with local or cloud pipelines, no extra keys). Add a cloud speech-to-speech "conversation mode" only where natural back-and-forth matters, with tools implemented as a thin, allow-listed proxy to Home Assistant.
- Barge-in with the HA pipeline is a client concern: stop the `<audio>` element and start a new run when the user presses talk again; there is no server-side truncation equivalent to OpenAI's WebRTC behaviour, so half-duplex push-to-talk is the honest UX. Wake-word-in-browser on iOS is impractical in a PWA (no background mic, screen-lock suspends audio); a wall display running a desktop-class browser could stream to `start_stage: "wake_word"` at the cost of constant upstream audio.
- Cost of cloud conversation is small at household scale: Gemini Live at about USD 0.023 per minute of two-way audio means 10 minutes a day is roughly USD 7/month; OpenAI Realtime is materially more expensive per the third-party figures.
- "Point the phone at a device and ask" is feasible two ways: a single still (`<input capture>` or `getUserMedia` frame) sent to a Cloud Function with the device registry as context so the model can resolve "this" to an `entity_id`; or a Live session with 1 FPS frames for conversational troubleshooting. A cheaper and more reliable alternative for identification is a printed QR/NFC tag per device that deep-links to its card.
- Chrome built-in AI is usable only on desktop Chrome and Chromebook Plus wall displays, for private, zero-cost extras such as rewriting notification text or classifying a typed command; it cannot be a dependency for iPhone/iPad.

### Gaps
- No measured end-to-end latency figures were found for OpenAI Realtime or Gemini Live from a browser; vendor pages say "low-latency" without numbers.
- OpenAI's official Realtime pricing page was not opened; model naming (`gpt-realtime-2.1` vs `gpt-realtime-2`) differs between sources, and GPT-Live's API availability is contradicted between the OpenAI guide and a third-party summary.
- iOS Safari/PWA specifics (microphone permission persistence in standalone mode, AudioWorklet behaviour, WebGPU availability on iPhone/iPad) were not verified this session.
- No authoritative benchmark was found for Moonshine vs Whisper in WebGPU on phone-class hardware.
- Gemini Live session-length limits, VAD configuration and the current deprecation status of `gemini-3.1-flash-live-preview` were not verified (one secondary source claims a 17 Nov 2026 shutdown; Google's pricing page still lists it).

## 7. Narrative and explanation

### Takeaway
Plain-language explanation of home telemetry is real but early: Emporia's conversational energy assistant answers "Why was my bill so high last week?" over an MCP server, small academic studies report high clarity and trust ratings for LLM-written energy feedback, and Google's Home Brief shows the failure mode when narratives are not grounded. The evidence that users value narratives is positive but thin and mostly self-reported.

### Cited Findings
- Emporia AI Energy Assistant (research release, 3 Dec 2025): a web assistant at assistant.emporiaenergy.com built on the Emporia MCP server and OpenAI's platform; example prompts include "Why was my bill so high last week?", "How much did it cost to charge my car in October?", "Is anything in my house using abnormal amounts of power?" and "What would happen if I moved my charging to off-peak hours?"; it builds custom visualisations and reports, flags unusual usage, and admits occasional errors — [Emporia blog](https://www.emporiaenergy.com/blog/meet-emporia-ai-energy-assistant/)
- EnergiQ (MDPI Sensors, 2025): households compared conventional dashboards with LLM-written messages over 6 to 8 months; participants rated message clarity 4.63 and contextual relevance 4.74, and 66% said it helped them make more informed energy decisions; recommendations were described as "personalized", "actionable" and "easy to trust" (search summary; pre/post questionnaire, not a controlled trial) — [EnergiQ paper](https://www.mdpi.com/1424-8220/25/16/4911)
- MELISSA (Energies, 2025) pairs an LLM interface with real-time feedback and concludes the LLM interface was the most decisive component for reducing consumption (search summary) — [MELISSA paper](https://doi.org/10.3390/en18143744)
- EcoMate (arXiv 2505.02802, May 2025): a GPT-3.5 chatbot for sustainable routines tested with 56 participants, rated higher on interaction satisfaction than a rule-based version (search summary) — [arXiv 2505.02802](https://arxiv.org/pdf/2505.02802)
- Octopus Energy's AI email assistant scored 76% customer satisfaction versus 72% for comparable human replies in an early trial; it is customer service, not a bill explainer (search summary) — [Octopus press release](https://octopus.energy/press/more-news-press-releases/octopus-energy-s-ai-trial-wins-customer-approval/)
- Bidgely announced what it calls the energy industry's first agentic AI customer experience on 21 Sep 2026 (press release title only; not opened) — [Utility Dive press release](https://www.utilitydive.com/press-release/20260921-bidgely-launches-energy-industrys-first-agentic-ai-customer-experience-sui-1/)
- Google's Home Brief (daily narrative of camera and home activity) drew mixed reception: The Verge called summaries closer to "fiction than fact", Android Authority described it as hit-or-miss, and Google added short clips beneath the brief so users can check its work (search summaries) — [The Verge](https://www.theverge.com/tech/813523/gemini-for-home-google-nest-camera-hands-on), [Android Authority](https://www.androidauthority.com/google-home-home-brief-feedback-3606539)
- Home Assistant building blocks for explanations: `recorder.get_statistics` action (2025.6), `ai_task.generate_data` with structured output (2025.8), LLM tools for historical statistics and logs (2026.11), the Activity trigger-chain dialog (2026.9), and the energy dashboard's Sankey, device hierarchy and per-device naming — [2025.6](https://www.home-assistant.io/blog/2025/06/11/release-20256/), [2025.8](https://www.home-assistant.io/blog/2025/08/06/release-20258/), [2026.11](https://www.home-assistant.io/blog/2026/11/04/release-202611/), [2026.9](https://www.home-assistant.io/blog/2026/09/02/release-20269/)
- Frigate's review reports and 0.18 "recap" tool are the camera-side equivalent of a narrated digest — [Frigate review summaries docs](https://docs.frigate.video/configuration/genai/genai_review), [Frigate v0.18.0](https://newreleases.io/project/github/blakeblackshear/frigate/release/v0.18.0)

### Inferences
- The reliable recipe for "why was the bill high yesterday?" is compute-then-narrate: a deterministic decomposition (yesterday vs trailing baseline per device from long-term statistics, tariff periods, weather, occupancy, solar yield) produces a ranked list of contributors with numbers; the LLM only turns that table into two or three sentences and picks a chart from the catalogue. That avoids the Home Brief failure mode and keeps the answer auditable.
- Since the household already has a weekly Gemini narrative, the step beyond is interactivity and grounding: tap any sentence to see the evidence chart; ask follow-ups; "explain this chart" on any card (pass the series summary, not pixels); and counterfactuals ("if the geyser had run at midday") computed deterministically.
- Narratives should be sparing: the research signal is that clarity and relevance drive perceived value, and the camera-brief reviews show that one confident error damages trust in the whole feature.

### Gaps
- No evidence was found of natural-language "why was my bill high" features from Octopus (consumer app), Tibber, Sense, Tesla or Span; searches for Sense and Span returned nothing relevant. Google Home energy explanations were not found.
- Sleep and health narrative summaries (for example wearables' daily readiness narratives) and evidence about their value were not researched (search budget exhausted).
- No controlled study comparing narrative vs chart-only presentations for household users was found; the cited studies are small and mostly self-report. A claimed University of Oxford finding of 27% more conservation actions appeared only as an unverified fragment and is not relied on.
- The papers above were not opened in full; figures come from search summaries.

## 8. On-device / local-first AI for privacy

### Takeaway
Home Assistant now has first-party local LLM paths (Ollama, and since 2026.8 llama.cpp and LiteLLM), a fully local voice stack (Whisper or Speech-to-Phrase plus Piper, microWakeWord on device), and Frigate runs vision, embeddings, face/plate recognition and transcription locally. Community consensus puts 8 to 9B Qwen-family models on a single consumer GPU as the practical floor for reliable tool calling; small fine-tunes handle basic control, while long-context reasoning, high-quality narrative and robust multi-step agency still favour cloud models.

### Cited Findings
- Home Assistant 2026.8 added **llama.cpp** (local server or any OpenAI-compatible endpoint, multiple agents with separate models and instructions) and **LiteLLM** (OpenAI-compatible proxy, one agent per configured model) as conversation-agent integrations — [2026.8](https://www.home-assistant.io/blog/2026/08/05/release-20268/)
- Ollama integration gained a `think` parameter option (2025.7); OVHcloud AI Endpoints offers EU-hosted open-weight models (2026.6); OpenRouter gives one interface to 400+ models (2025.8) — [2025.7](https://www.home-assistant.io/blog/2025/07/02/release-20257/), [2026.6](https://www.home-assistant.io/blog/2026/06/03/release-20266/), [2025.8](https://www.home-assistant.io/blog/2025/08/06/release-20258/)
- Local voice: Speech-to-Phrase (closed-vocabulary STT) runs on a Raspberry Pi 4 or Home Assistant Green and supports 6 languages with 15 more in progress; Piper covers 39 languages/dialects; Whisper plus Piper is the "Full Local" tier; Speech-to-Phrase cannot fall back to an LLM because unexpected commands are not transcribed — [Voice chapter 10](https://www.home-assistant.io/blog/2025/06/25/voice-chapter-10/)
- Dual wake words let one satellite route one wake word to a fully local pipeline and another to a cloud/LLM pipeline — [Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11)
- Built-in Assist handles lights, locks, media, timers, to-dos and delayed commands in dozens of languages with no LLM — [Voice chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11)
- Community model guidance for 2026 (blogs; search summary): Qwen3 8B or Qwen3.5 9B on an 8 GB GPU as the common pick for tool calling; Llama 3.2 3B or Home-LLM fine-tunes (Home-Llama-3.2-3B, Home-FunctionGemma-270m) on low-power hardware; larger Qwen 27B/35B on 24 GB+ GPUs; the Ollama model must carry the "tools" capability; Home Assistant's Ollama integration defaults to an 8K context window and exposed entities consume it; Gemma 4 reasoning traces can hide tool calls unless thinking is disabled — [promptquorum guide](https://www.promptquorum.com/smart-home/best-local-llm-models-smart-home), [botmonster guide](https://botmonster.com/smart-home/build-private-local-ai-voice-assistant-2026/)
- Frigate's local vision recommendations: `qwen3-vl` (best at small objects and interactions), `qwen3.6`/`qwen3.8` and `gemma4` (good situational understanding); 8 GB for 7B, 16 GB for 13B, 24 GB for 33B; CPU inference not recommended; Frigate 0.17 runs detection on Intel NPUs via OpenVINO, Apple Silicon NPU via a host-side detector, and RKNN NPUs — [Frigate GenAI config docs](https://docs.frigate.video/configuration/genai/genai_config), [Frigate v0.17.0](https://github.com/blakeblackshear/frigate/releases/tag/v0.17.0)
- Home Generative Agent supports Ollama or any OpenAI-compatible local server (vLLM, llama.cpp, LiteLLM), local faster-whisper (about 2 GB VRAM recommended for large-v3-turbo) and local Piper or Kokoro TTS — [home-generative-agent](https://github.com/goruck/home-generative-agent)
- The community AI guide names Apple M-series, AMD Strix Halo / Ryzen AI Max and NVIDIA DGX Spark as local-inference hardware families and advises sizing by workload (speech, LLM, vision, embeddings, background tasks), noting that "prompt processing can dominate latency" — [HA community guide](https://community.home-assistant.io/t/so-you-want-to-ai-in-home-assistant/1021777)
- Chrome's built-in Gemini Nano keeps data on the device ("no data is sent to Google or third parties during use") but is desktop/Chromebook Plus only — [Chrome Prompt API docs](https://developer.chrome.com/docs/ai/prompt-api)
- Open Home Foundation position: AI is never required and is opt-in, with local and cloud models both supported (search summary) — [OHF newsletter](https://newsletter.openhomefoundation.org/ai-is-optional-privacy-isnt/)

### Inferences
- Tasks local models handle well in 2026: wake word, STT/TTS, closed-vocabulary and fuzzy intent matching, simple device control with a small exposed-entity set, structured extraction with a schema (`ai_task` with `structure`), camera event descriptions and threat triage on a mid-range GPU, embeddings and semantic search, face and plate recognition, audio transcription.
- Tasks that still benefit from cloud models: multi-step agentic reasoning over many tools, large-context analysis (weeks of history, long logs), high-quality narrative writing, generative-UI spec composition with a large catalogue, real-time speech-to-speech conversation, and fine-grained visual understanding of small or distant subjects.
- A privacy-preserving split for this household: keep all camera pixels local (Frigate with a local VLM, or text-only summaries leaving the LAN), send only aggregated numeric telemetry and Frigate's text descriptions to the cloud model used for narratives and UI composition, and strip names, plates and addresses before cloud calls (HGA's redaction of network identifiers is a precedent).
- LiteLLM (2026.8) is a pragmatic router: one Home Assistant agent per model lets the front end or pipeline choose local-first with cloud fallback per task without changing code.

### Gaps
- No authoritative benchmark of local models on Home Assistant tool calling was found; the model recommendations come from unofficial blogs with internal inconsistencies and should be tested against the actual entity set.
- NPU mini-PC specifics (which NPUs can run 8B-class LLMs at usable speed, as opposed to detection models) were not verified.
- The current state of the Home-LLM (home-llm) custom integration and its model line-up was not checked at source.
- Power draw and running cost of an always-on local GPU box versus cloud API spend were not quantified.
